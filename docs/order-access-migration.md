# 订单查询权限迁移与恢复

新订单创建时返回一次独立的 256 位查询凭据；数据库仅保存绑定订单号的摘要。查询、换支付渠道和重新获取二维码均须使用请求头 `X-GetToken-Order-Access`。普通订单号不再代表读取权限。它不是用户的 Session Key。

浏览器保存最近五单的查询凭据，复制按钮提供带 fragment 的私密链接。打开后立即清理 fragment；凭据不进入 HTTP query 或访问日志。共享电脑不要保存链接，离开时清理站点存储；链接遗失由服务方核实订单所有权后恢复，不能以提供 Session Key 作为恢复证明。

## 存量迁移

安装器在切换运行版本前执行候选版本的 `access-check`。存在未配查询凭据的历史订单时，检查失败，旧版本继续运行，网站部署也不得继续；直接启动新服务同样会拒绝。数据库变更只增加字段，订单、支付、退款和加密密钥均保留。

1. 先关闭新增接单，保留旧服务对账及退款。备份并只读核对订单数量、状态和可用的私密联系途径。
2. 在服务器加载已有受保护环境，用候选版本 CLI 执行 `access-check`；该命令只打印待迁移数量，不打印凭据。
3. 为确认所有权且能私密交付的历史订单执行 `issue-access ORDER_ID /绝对私有路径/query.json`。候选版本尚未激活时，必须使用候选目录内 CLI，而非仍指向旧版本的安装命令。以服务用户运行，输出目录仅该用户可读写；文件自动采用 0600 且拒绝覆盖已有文件。
4. 将文件内查询链接通过已核实的私密渠道交给该订单用户，并登记已送达。文件不入仓库、工单、日志或网站目录。没有恢复渠道时停止迁移，不得给无人认领的订单批量生成后就宣布完成。
5. 全部历史订单完成交接、`access-check` 通过、服务开关仍关闭后再部署，并实际抽验历史查询、付款补单和退款。

若需提前在候选版本执行 CLI，在受控服务器 shell 内加载 `/etc/gettoken/verify.env`，使用安装目录的 Node 22 和候选版本的 `server/verify/cli.mjs`；不要复制或打印环境变量值到聊天。

## 凭据遗失

核实支付记录与订单所有权、记录处理人后，使用 `rotate-access ORDER_ID /新的绝对私有路径/query.json`。旧凭据立即失效，财务状态不变。数据库事件只记操作类型，不记新旧凭据。重复输出路径会报错，不覆盖任何文件。

2026-10-16 本轮生产只读盘点确认订单总数 0、未迁移 0、待退款 0；候选安装器再次确认未迁移数量为 0 后发布。没有历史用户需要签发恢复链接，没有删除订单或绕过检查。证据见 [合并记录](merge-acceptance-2026-10-16.md)。未来如有存量，迁移报告仍必须记录凭据签发和私密交付情况；机器检查不证明用户已收到。

## 索引与回滚

公开 `/verify/` 保留索引；带订单参数的介绍壳和后台壳返回服务端 noindex/no-store，订单 API 需认证且禁止缓存。后台登录 HTML 允许抓取以读取 noindex，后台数据仍受会话保护。

启用后不得回滚到仅凭订单号读取的旧 API。优先关闭新增接单并前向修复；不要恢复旧数据库覆盖付款、退款或查询摘要，也不要更换 `VERIFY_SECRET`。
