## 一、本轮目标和边界

本轮目标是：消除错单审核风险，让普通商品的询价入口真实可用，让审核服务具备明确的开放门槛，并提升现有页面回答用户问题的能力。

三个产品决策：

1. **普通商品采用询价模式。** 五个商品页暂不新建商城订单、库存、在线支付和自动交付系统。报价、核款、交付由真实支持渠道承接，并人工登记询价记录。付款备注码不能称为订单号。没有支持渠道时明确暂停受理，不能宣称询价闭环完成。
2. **审核服务独立验收。** 沿用现有微信、支付宝订单与退款后端；代码合并不自动打开接单。服务定义、授权必要性、商户配置和真实到账验证均满足后，才能对外开放。
3. **优先完善现有 28 页。** 保留 URL、静态生成架构、布局、配色和组件。内容改源文件，再重新生成 HTML。暂不新增同义词落地页、独立信任页面或做移动端布局改版。

“不修改页面”的既有约束在本方案中按以下边界处理：文案修正不改变视觉结构；PR-01、02、04、05 提议修改必要的交互或请求逻辑，属于本方案明确列出的功能修复范围，不混入样式改版。这些改动已按本轮实施，逐项结果以验收记录为准。若后续仍要求 JavaScript 逻辑也完全不变，相应缺陷不能宣称已修复，后台须继续使用显式订单号 CLI，相关业务维持关闭。

已有 FAQ、提示、对话框和正文承载本轮服务信息；若必要披露无法在现有组件中清晰呈现，应保持相关服务关闭，并单独提出页面扩展方案，不能缩小字号或隐去重要条件凑版面。

## 三、每个 PR 的开发与验收范围

### PR-01：审核后台错单修复

**问题与结果：** A 的迟到响应可覆盖 B 的详情，操作却提交给 B。修复后任何审核动作都绑定用户当前看到并确认的订单。

**主要文件：** `assets/gettoken/verify-admin.mjs`；新增有意义的浏览器竞态回归用例；必要时更新 `docs/verify-admin-race-proposed.patch` 为已实施说明。

开发项：

- 详情请求使用递增版本或等效机制，丢弃已失效响应；不能只依靠请求取消。
- 切换时清除旧详情的可操作状态；加载失败、退出登录、会话失效后不能沿用旧订单操作。
- 提交绑定已呈现详情的 ID；确认文本显示订单号和脱敏识别信息。确认后再次核对当前详情，防止切单和重复提交。
- 审核动作的迟到响应不能覆盖另一个订单；同样保护筛选、分页和搜索列表的乱序结果。
- 沿用现有对话框、按钮与样式，不新建视觉组件。

验收：延迟 A、先返回 B、再返回 A；A→B→A；详情失败；提交中切单；重复点击；会话失效；快速筛选分页。逐项核对显示 ID、确认 ID、请求 ID 和数据库记录，未选中的订单保持不变。测试必须能在修复前复现至少一个错单场景。

回滚：若出现回归，暂停网页审核，使用现有 `gettoken-verify decision ORDER_ID ...`。不能回滚到有错单风险的版本后继续正常使用后台。

### PR-02：普通商品询价与客服闭环

**问题与结果：** 空价格、空二维码和空客服目前仍进入购买弹窗。改为统一的受理状态，用户能明确下一步。

**主要文件：** `assets/gettoken/catalog.mjs`、`site.config.mjs`、`shop.mjs`、`product.mjs`；`content/products.mjs`、`scripts/build-site.mjs` 及对应生成页。

开发项：

- 定义商品级 `unavailable` / `inquiry` 状态及可检查的启用条件。本轮不提供普通商品自动付款状态。
- 只有实际可接单且联系渠道可用时显示“咨询报价”；其余显示“暂未受理”等真实状态。首页、商品卡、弹窗、FAQ 和导航采用同一口径。
- 复用现有联系方式弹窗，提供选中产品、档位、期限的咨询摘要；不向用户索取账号密码或 Session Key 作为普通询价资料。
- 隐藏或停用未配置的付款动作；不显示 `¥XX`、`$XX`、待上传收款码等占位付款信息。没有报价时不计算虚假优惠或总价。
- 官网参考价格与本站报价分开。保留现有选择组件，不能把未确认的季度/年度供应显示为可购买。
- 真实支持方建立人工登记约定：询价编号、商品、报价有效期、交付条件、处理人、状态。浏览器生成的付款备注不能充当服务端订单或付款证明。
- 在现有区域说明真实服务主体、联系渠道、支持时段及报价前确认项；不编造公司资质和响应时长。

验收：覆盖五商品×三档位、现有期限选择、联系渠道缺失/部分/完整、手机和桌面弹窗、键盘退出、无 JavaScript 的状态文案。配置缺失时无假付款承诺；配置完整时联系入口确实可打开，支持方可接收测试咨询并找到人工登记记录。

资料未到时：可合并“暂停受理”的安全状态，验收只能写“错误购买入口已修复”，不能写“询价已开通”。回滚或降级必须保持 unavailable，不能恢复假付款入口。

### PR-04：审核服务定义与开放门槛

**主要文件：** `assets/gettoken/verify-rules.mjs`、`verify.mjs`、`scripts/build-site.mjs`；`server/verify/config.mjs`、`service.mjs`、`app.mjs` 按需调整；服务规则与运营文档。

开发项：

- 以服务负责人确认的内容明确服务动作、不能处理的情形、成功证据、客户验收、超时升级、失败及退款条件。保留“Claude KYC认证”既有标题要求，在现有醒目说明中清楚界定第三方协助与官方结果。

验收：off/live 及接单开关组合、接口不可达、错误输入、重复提交、未付款、处理中、通过、失败、退款处理中/异常均有准确说明与下一步。关闭时不鼓励输入敏感值；已付款订单仍能继续处理。文案和状态测试使用虚构凭据。

阻断项：无可确认的交付标准、必要授权或真实支持渠道，则仅合并关闭状态及说明修复，不开放收款。

### PR-05：私有订单访问与索引隔离

**主要文件：** `server/verify/app.mjs`、`service.mjs`、`store.mjs`、`secure.mjs`；`assets/gettoken/verify.mjs`；`scripts/configure-seo-routing.py`、`nginx-seo-locations.conf`、`check-live-seo.mjs` 和相关测试。

开发项分成两部分，不能用 noindex 代替权限控制：

1. **访问与缓存。** 新订单采用独立高熵查询凭据，服务端只保留校验摘要；订单号不再单独授予读取权限。凭据不能出现在普通 query、分析事件或日志中。可采用 fragment 链接交接后清理地址、请求头传递等方案，沿用现有查询区域，不添加账户注册系统。所有读取、付款二维码获取等相关用户接口统一检查授权，支付平台通知仍走现有验签通道。响应保持 no-store，限制返回字段，防止跨订单读取。
2. **索引。** `/verify/` 无订单参数的介绍页可索引；包含订单参数的 HTML 响应及订单 API 由服务端输出正确的 noindex/no-store，使用 `X-Robots-Tag` 等可实际验证的响应头。后台登录壳允许爬虫读取 noindex 时，管理数据仍由 API 认证保护；从 sitemap 排除，避免同时用 robots 阻挡该 noindex 的读取。

迁移要求：上线前只读盘点存量订单与浏览器历史查询方式。无存量可直接切换；有存量必须先交付凭据补发/身份核验恢复和客服流程，并验证历史支付退款仍工作。不能删除历史订单，不能批量暴露查询凭据，不能无限期保留“仅凭订单号”绕过。若无法安全迁移，本 PR 暂缓上线，新增接单保持关闭。

验收：无凭据、错误凭据、跨订单凭据均不能读取私有状态；正常创建后的查询、刷新、历史记录和恢复流程可用；已有订单支付与退款不受影响；公开页、订单参数页、API、后台在本地 Nginx/TLS 和上线后真实 HTTP 响应分别核验；日志与复制链接无 Session Key。授权凭据与用户提交的 Session Key 必须是不同概念。

回滚：新增字段向后兼容，保留财务数据及 `VERIFY_SECRET`。一旦启用强制查询授权，不得回滚到绕过授权的旧 API；优先关闭新增接单并前向修复。

- 多管理员角色体系、复杂工单平台、全文搜索、CMS、框架迁移或微服务化。
- 移动端布局重做、字体/配色/组件重设计、批量新增 SEO 页面或无数据支撑的 URL 合并。
